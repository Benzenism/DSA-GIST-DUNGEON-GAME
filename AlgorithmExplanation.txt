01. Dungeon Map (던전 맵 및 맵 생성)

사용된 자료구조/알고리즘: 2D Grid (2차원 리스트) 및 BFS (너비 우선 탐색)
맵 생성 과정 상세: 먼저 전체 맵을 벽(TILE_WALL)으로 채운 뒤, 설정된 최소/최대 방 크기 범위 내에서 사각형 형태의 방들을 무작위 좌표에 생성합니다. 이때 방들이 서로 겹치지 않도록 교차 검사를 수행하며 통과된 방들만 리스트에 추가합니다. 이후 이전 방과 현재 방의 중심점 좌표를 기준으로 기역자(L자) 형태의 복도를 뚫어 바닥 타일(TILE_FLOOR)로 연결합니다. 마지막으로 플레이어가 시작하는 첫 번째 방을 기준으로 사방으로 퍼져나가는 BFS 탐색을 수행하여, 시작점에서 물리적으로 '가장 멀리 떨어진 바닥 타일'의 위치를 찾아내어 탈출 계단(TILE_STAIR)을 배치함으로써 도달 가능성과 게임의 완급 조절을 동시에 보장합니다.
선택 근거: 타일 기반 던전의 고정된 격자 좌표 평면을 가장 직관적으로 표현하고 관리하기 위해 2차원 리스트를 선택했습니다. 인덱스 조회를 통해 특정 좌표의 지형 상태를 즉각적으로 파악할 수 있어 게임 화면 렌더링 및 충돌 검사에 최적입니다.
대안과의 차이점: 인접 리스트 그래프 형태와의 비교: 인접 리스트는 빈 공간(벽)의 메모리를 아낄 수 있지만, 특정 (X, Y) 좌표가 이동 가능한 바닥인지 확인할 때마다 리스트를 순회해야 하므로 탐색 효율이 떨어집니다.
2차원 리스트를 사용하지 않을 경우의 단점 (1차원 리스트 또는 딕셔너리): 데이터를 1차원 리스트로 풀어서 관리하면 매번 'Y * 전체 가로 폭 + X'와 같은 인덱스 변환 연산을 추가로 수행해야 하므로 코드의 직관성이 크게 저하됩니다. 또한 좌표를 키(Key)로 하는 딕셔너리 형태로 맵을 관리하면, 벽과 바닥이 바뀔 때마다 해시 조회 오버헤드가 발생하며, 매 프레임 전체 격자를 순회하며 화면을 그려야 하는 게임 루프 특성상 렌더링 성능에 병목이 생길 수 있습니다. 따라서 연속된 메모리 공간을 활용하는 2차원 리스트가 가장 효과적입니다.
시공간 복잡도: 타일 상태 조회 및 갱신의 시간 복잡도는 O(1)이며, 계단 배치를 위한 BFS 탐색은 최악의 경우 맵의 모든 바닥을 방문하므로 O(V + E)가 됩니다. (V는 바닥 타일 수, E는 인접 타일 간 연결선 수) 공간 복잡도는 맵의 가로 세로 크기에 비례하는 O(Rows * Cols)입니다.
코드 위치: map_gen.py 파일의 DungeonMap 클래스 (self.tiles 변수, _find_farthest_room_bfs() 및 generate_map() 메서드)

02. Undo System (되돌리기 시스템)

사용된 자료구조/알고리즘: 스택 (Stack) (list.append() 및 list.pop() 활용)
선택 근거: 플레이어가 직전에 수행한 행동을 역순으로 거슬러 올라가며 취소해야 하므로, 가장 마지막에 발생한 게임 상태를 가장 먼저 꺼내어 복원하는 후입선출(LIFO) 특성의 스택 구조가 시스템 논리에 완벽히 부합합니다.
대안과의 차이점: 큐(Queue)를 사용하게 되면 가장 먼저 수행했던 게임 시작 직후의 1턴 상태로 돌아가 버리기 때문에 되돌리기 시스템을 구현할 수 없습니다. 또한 게임 상태의 '변화량(Delta)'만 기록하는 방식은 메모리를 약간 아낄 수 있으나, 몬스터의 스폰이나 삭제, 턴 매니저의 내부 인덱스 등 복합적인 상태가 꼬여 버그를 유발하기 쉽습니다. 파이썬의 deepcopy를 이용해 턴 종료 시점의 전체 스냅샷을 스택에 푸시하는 방식이 구현이 명확하고 상태 복구의 무결성을 완벽하게 보장합니다.
시공간 복잡도: 상태를 스택에 넣고(Push) 빼는(Pop) 연산 자체의 시간 복잡도는 O(1)로 극도로 빠릅니다. 공간 복잡도는 설정된 최대 되돌리기 제한 수 N과 한 턴의 게임 상태 데이터 크기 S에 비례하여 O(N * S)의 고정된 메모리를 사용합니다.
코드 위치: game_screen.py 파일의 GameScreen 클래스 (self.undo_stack 변수, _push_undo() 및 _pop_undo() 메서드)

03. Turn Management (턴 관리)

사용된 자료구조/알고리즘: 큐 (Queue) (collections.deque 활용)
선택 근거: 플레이어와 생성된 적들이 공평하게 순서대로 돌아가며 한 번씩 행동을 주고받는 순환형 라운드 로빈(Round-Robin) 시스템을 구축하기 위해, 먼저 들어온 유닛이 먼저 행동하는 선입선출(FIFO) 특성의 큐를 사용했습니다.
대안과의 차이점: 만약 유닛마다 '민첩성' 같은 스탯이 존재하여 실시간으로 다음 행동 순서가 요동치는 게임이라면 '우선순위 큐(Priority Queue)'가 필요합니다. 그러나 본 게임은 모든 객체가 한 번씩 고정적으로 턴을 소모하는 정적 구조입니다. 우선순위 큐를 쓰면 정렬 유지를 위해 매번 O(log N)의 삽입 연산 비용이 들지만, 양방향 큐인 deque를 활용하면 턴 교대 처리를 O(1)이라는 최소한의 비용으로 깔끔하게 처리할 수 있어 최적화에 유리합니다.
시공간 복잡도: 현재 턴 유닛 조회 및 행동 완료 후 큐의 맨 뒤로 보내는 교대 연산의 시간 복잡도는 O(1)입니다. 공간 복잡도는 현재 던전 층에 존재하는 활성화된 총 액터 수 A에 비례하므로 O(A)입니다.
코드 위치: turn_manager.py 파일의 TurnManager 클래스 (self._queue 자료구조 및 advance() 메서드)

04. Item Inventory (아이템 인벤토리)

사용된 자료구조/알고리즘: 해시맵(딕셔너리) (Hash Map / Dictionary)
선택 근거: 플레이어가 던전에서 아이템을 습득하거나 소비할 때, 아이템의 이름(Key)을 기반으로 현재 가방에 해당 아이템이 몇 개(Value) 남아있는지 실시간으로 조회하고 수량을 직관적으로 업데이트하기 위해 해시맵 구조를 채택했습니다.
대안과의 차이점: 리스트 자료구조와의 비교: 일반 리스트를 사용하면 특정 아이템을 가지고 있는지 검사하거나 개수를 수정할 때마다 리스트의 첫 항목부터 끝까지 순회해야 하는 O(I)의 선형 탐색 병목이 발생합니다.
해시테이블 대신 해시맵(딕셔너리)을 선택한 이유: 전통적인 해시테이블(HashTable)은 멀티스레드 환경을 고려한 동기화(Synchronization) 락 메커니즘이 내장되어 있어 단일 스레드로 돌아가는 일반적인 Pygame 루프 환경에서는 불필요한 연산 오버헤드를 발생시킵니다. 반면 파이썬의 내장 딕셔너리는 동기화 처리가 없는 순수 해시맵 구조로 구현되어 있어 데이터 접근 속도가 극도로 빠릅니다. 추가로 파이썬 3.7 버전 이후의 딕셔너리는 아이템이 추가된 순서(Insertion Order)를 내부적으로 유지해 주므로, 인벤토리 UI 창에 아이템을 획득한 순서대로 깔끔하게 정렬하여 보여주기에도 매우 유리합니다.
시공간 복잡도: 아이템 존재 여부 확인, 개수 추가, 아이템 사용에 따른 데이터 조회 및 수정의 평균 시간 복잡도는 O(1)입니다. 공간 복잡도는 캐릭터가 한 번이라도 소지했던 고유 아이템 종류의 총 개수 I에 비례하므로 O(I)입니다.
코드 위치: player.py 파일의 Player 클래스 (self.inventory 변수, pick_up() 및 use_item() 메서드)

05. Enemy AI (적 AI 유닛 인공지능)

사용된 자료구조/알고리즘: A* 경로 탐색 알고리즘 및 최소 힙 (Min-Heap / heapq)
선택 근거: 던전의 벽과 장애물을 영리하게 피해 플레이어의 현재 위치까지 가장 짧은 경로로 추적해 오는 지능적인 몬스터를 구현하기 위해 A* 알고리즘을 사용했습니다. 탐색 과정에서 누적 이동 비용과 남은 예상 거리를 더한 총 예상 비용(F-Score)이 가장 낮은 타일을 최우선으로 선택해야 하므로, 최솟값을 O(1) 성능으로 즉각 추출할 수 있는 최소 힙을 연산의 중심 자료구조로 활용했습니다.
대안과의 차이점: BFS(너비 우선 탐색)와의 비교: BFS도 최단 경로를 찾아내지만, 목적지의 방향을 전혀 고려하지 않고 사방으로 무조건 퍼져나가며 맹목적인 탐색을 수행하므로 맵이 넓어질수록 쓸데없는 연산량이 기하급수적으로 증가합니다.
다익스트라(Dijkstra) 알고리즘을 사용하지 않은 이유: 다익스트라 알고리즘은 가중치가 있는 그래프에서 훌륭한 최단 경로를 보장하지만, BFS와 마찬가지로 목표점의 위치를 모른 채 출발점 기준 사방으로 탐색 반경을 넓혀가는 방식을 취합니다. 반면 A* 알고리즘은 현재 위치에서 플레이어까지의 직선 거리(휴리스틱 함수: 맨해튼 거리)를 계산하여 플레이어가 있는 방향의 타일들을 우선적으로 탐색합니다. 따라서 목적지가 고정된 추적 AI 상황에서는 다익스트라보다 탐색 영역을 극적으로 좁힐 수 있어 연산 효율이 압도적입니다.
시공간 복잡도: 최소 힙을 통한 노드 추출 및 완화 연산으로 인해 시간 복잡도는 최악의 경우 O(E log V)가 되지만 휴리스틱 덕분에 실제 연산량은 훨씬 적습니다. 공간 복잡도가 O(V)인 이유는, 탐색 도중 경로를 역추적하기 위해 방문한 타일들의 연결 관계를 기록하는 came_from 딕셔너리와 가중치를 저장하는 g_score 딕셔너리에 최악의 경우 던전 내 모든 바닥 타일(V)의 정보가 누적되어 저장되기 때문입니다.
코드 위치: enemy.py 파일의 Enemy 클래스 (_astar() 및 astar_step() 메서드)

06. Leaderboard (리더보드 점수판)

사용된 자료구조/알고리즘: 파이썬 내장 다중 키 정렬 알고리즘 (Timsort / list.sort())
대안(Quick Sort, Merge Sort 등)을 사용하지 않은 이유: 퀵 정렬(Quick Sort)을 쓰지 않은 이유: 리더보드는 '클리어 여부 -> 최종 점수 -> 되돌리기 횟수 -> 소요 시간 -> 소모 턴 수'라는 5단계의 까다로운 다중 우선순위 조건(Multi-key)을 기반으로 정렬되어야 합니다. 퀵 정렬은 동일한 우선순위를 가진 데이터의 상대적 위치가 정렬 후 뒤바뀔 수 있는 '불안정 정렬(Unstable Sort)'입니다. 따라서 여러 조건으로 정렬을 연이어 수행할 때 이전 정렬 결과가 망가질 위험이 있어 리더보드 시스템에 부적합합니다.
병합 정렬(Merge Sort)을 직접 쓰지 않은 이유: 순수 병합 정렬은 정렬 과정에서 원본 배열과 똑같은 크기의 추가적인 메모리 공간(O(N))을 매번 새로 할당해야 하는 낭비가 있습니다. 반면 내장 Timsort는 내부 최적화를 통해 메모리 오버헤드를 최소화합니다. 무엇보다 파이썬의 list.sort()는 C언어로 컴파일되어 정밀하게 튜닝되어 있으므로, 파이썬 코드로 퀵 정렬이나 병합 정렬을 직접 구현해 사용하는 것보다 훨씬 빠르고 안정(Stable) 정렬 특성을 완벽히 지원하므로 선택했습니다.
시공간 복잡도: 리더보드 파일에 저장된 전체 유저 기록의 수를 N이라고 할 때, 정렬에 소모되는 시간 복잡도는 O(N log N)입니다. 로컬 JSON 파일을 읽어와 파이썬 리스트 객체로 메모리에 적재하므로 공간 복잡도는 O(N)입니다.
코드 위치: leaderboard.py 파일의 save_entry() 함수 내부 (board.sort(key=lambda e: ...) 구문)
